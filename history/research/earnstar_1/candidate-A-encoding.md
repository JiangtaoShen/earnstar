# Candidate A — "Don't destroy my file's encoding or line endings" (S024)

**Erratum (S024, after the independent critique; `critique.md`, ADR-006 section)**: §3 and §6 are wrong in three places and incomplete. Codex shipped CRLF preservation behind an opt-in flag (`apply_patch_preserve_line_endings`, PRs #37757 and #37758 merged 2026-08-10, release 0.148.0); Kilo (27k stars) has preserved legacy encodings natively since 2026-04; mcp-file-tools and agent-tool document Codex setups; the repair idea of §4 was published with 99.2 % recovery in [claude-code#7134](https://github.com/anthropics/claude-code/issues/7134#issuecomment-5388799038) (2026-08-23); about 25 further small tools exist (`s024/critique-ADR-006.md` §2). The prototype also failed under `core.autocrlf=true` and with Windows-1252 bytes 0x80–0x9F. The text below is kept as written.

Evidence of the need: `needs.md` §A and `s024/needs-G1-windows.md` (N1, N2, N6). This file records the job as users experience it, the existing solutions as actually tried, and the prototype.

## 1. The job, step by step (as the people in the evidence describe it)
1. A developer works in a codebase whose files must stay in a legacy encoding or in CRLF: the toolchain requires it ("The encoding is mandated by the toolchain and can't be changed", [claude-code#7134](https://github.com/anthropics/claude-code/issues/7134#issuecomment-4922011057)), or the team's editors and diffs assume it (Visual Studio, VBA, Delphi, batch files).
2. They ask an AI coding agent (Claude Code, Codex, OpenCode, Gemini CLI) for an ordinary change. The task never mentions encodings.
3. The agent's file tools decode the file as UTF-8. Every byte sequence that is not valid UTF-8 becomes U+FFFD (or, for some byte pairs, an unrelated valid character), so the agent sees garbage where the comments and strings were.
4. The agent edits and writes the file back as UTF-8, sometimes with LF line endings. Every non-ASCII character in the whole file is now destroyed, even on lines the agent did not touch ("an ASCII-only edit … still corrupts every non-ASCII byte", [#7134](https://github.com/anthropics/claude-code/issues/7134#issuecomment-4923969362)).
5. The developer finds out later: the build breaks, a diff shows the whole file changed, Visual Studio warns about line endings, or a Japanese or Chinese comment is gone. Fixing it costs tokens and time ("fixing the errors generated by this issue consumes a lot of tokens", [#7134](https://github.com/anthropics/claude-code/issues/7134#issuecomment-3376508934)); the common belief is that the replaced characters cannot be recovered, so people `git checkout` the file and lose the agent's work, or redo it by hand.
6. Workarounds people built: prompt rules (ignored), converting the repo to UTF-8 (often not allowed), hooks with iconv or chardet, a Task Scheduler file watcher that fixes line endings, an OpenCode plugin, MCP servers the model must remember to use.

## 2. Reproduced on this machine (S024 log 06:16–06:36)
- The developer's own Edit tool (Claude Code 2.1.287, desktop engine) and the standalone CLI's Read tool both decode GBK and Shift_JIS as U+FFFD.
- Realistic fixture (`lab/s024/fx/make.py`: a small point-of-sale project in git with GBK + CRLF C sources, a Windows-1252 VBA module, a Shift_JIS utility file; a user-style prompt asking for three code changes):

| Agent setup | Result |
|---|---|
| Opus 5.5, all tools (×2) | Inspected the bytes, edited through `iconv` and Python; everything kept |
| Opus 5.5, Read/Edit/Write/Glob/Grep | First edit destroyed `jp/util.c` (34 U+FFFD); it noticed, stopped, and told the user to restore from git |
| Opus 5.5, same tools + claude_encoding_guard | All changes made, all encodings and line endings kept |
| Sonnet 5.5, all tools | Careful (PowerShell, Bash); everything kept |
| Haiku 4.5, all tools | Said "Done!" after deleting every Chinese comment, translating the Chinese receipt strings into English, converting CRLF to LF, and saving the VBA module as UTF-8 |

So the newest large models notice and work around the problem when they have a shell, at a cost; a fast model destroys content silently; and every model is exposed when it uses the built-in edit tools, which is the default path the agents are told to prefer.

## 4. Prototype (S024 log 06:47–06:50; `lab/s024/proto-a/keepenc.mjs`, throwaway, Node, no dependencies)
- **What it does**: for each file changed since `HEAD` (or against a backup folder), detects the original encoding, BOM, and line endings from the original bytes, detects what changed, and rebuilds the file: unchanged lines come back byte for byte; edited lines keep the agent's new text, and every character the agent copied from the damaged view is aligned back (character-level LCS over an exact WHATWG lossy decoder with byte offsets) to the original bytes and decoded in the original encoding; the result is re-encoded in the original encoding with the original line endings and BOM. It warns when non-ASCII text of the original is gone (deleted or rewritten).
- **Tested on real damage** (four sets of files damaged by agents in this session): every U+FFFD-damaged file came back as the original plus exactly the intended change, valid in its original encoding and line endings, including the Chinese comment on the edited line. For Haiku's files it restored encodings and CRLF and warned about 69, 6, and 4 lost non-ASCII characters (deleted or translated text, which no tool can restore).
- **Gaps found**: a file whose non-ASCII text was entirely deleted looks like plain ASCII and is not flagged; detection on very short files needs care (two bugs fixed during the test); new text the agent writes that the original encoding cannot represent (an emoji in a GBK file) must be reported, not silently replaced.

## 5. What a first version would be
- **CLI** (`npx <name> check | fix`, zero dependencies, Windows/macOS/Linux): compare changed files with `HEAD` or the index; restore encoding, line endings, and BOM; recover damaged characters; report lost text. `check --staged` as a git pre-commit hook works for any agent or editor.
- **Claude Code plugin**: PreToolUse (Edit, Write) keeps a snapshot of the original bytes; PostToolUse repairs the file against the snapshot at once and, when text was lost, tells the model the real text of the lines it changed. No `uv`, no temporary UTF-8 file on disk.
- **Codex and OpenCode**: hook and plugin recipes built on the same CLI. Both agents run with local models through Ollama (`codex --oss`; OpenCode's Ollama provider), so they can be tested end to end on this machine without accounts (to be verified in P2).

## 6. Risks
- A native fix in Claude Code would shrink the Claude Code part; the CLI, the repair of damage already done, and the other agents and editors would remain.
- The newest models increasingly work around the problem themselves when they have a shell.
- The people who need it may wait for the vendor rather than search; the existing plugins' low adoption (1–45 stars) is a warning.
- The project's README must be in English (Constitution §9), while many of these users search in Chinese or Japanese; a translated README needs the owner's approval (§3B). Test fixtures with CJK text must be generated from code points, because the repo's content check rejects Chinese text.
